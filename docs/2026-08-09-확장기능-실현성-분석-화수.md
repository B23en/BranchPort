1. 회의 To-Do 중 **3개는 feat/compact에서 이미 구현·실측까지 끝났다** (평가 지표, 범위 밖 정보 보존, 목적별 요약 전략). 중복 작업하면 안 되는 영역.

5. 회의 메모의 "노드별 한줄 요약(claude -p)"은 **이미 main에 있다** (`/api/label`, labels 캐시). 새로 만들 항목이 아니라 위 retrieval의 재료다.

## 1. 이미 끝난 To-Do — 중복 작업 금지 (feat/compact, MS.LIM)

회의 확장 To-Do 목록과 feat/compact를 대조한 결과:

- **"평가 지표 구상 + 간단하게 실제로 해보기"** → 끝났고 회의 기대치를 넘음. QA 보존율 파일럿 실측(SWE-chat 13세션·130문항, 프롬프트 개선으로 86%→92%), 목적 프로파일 A/B(4세션×4조건×10문항: continue 85%·bugfix 83%·none 80%·handoff 75%→가드 추가), 지표 조사 문서 563줄(SummaC 1순위, key-fact recall 자동채점, Githru식 과제완료시간 A/B 제안 포함).
- **"범위 밖 손실 중요 정보 보존 전략"** → 구현됨. `glossary.ts` 용어 부록: 압축 범위 안에서 참조되지만 정의가 범위 밖(조상 턴)에 있는 식별자를 기계 추출 → 조상 스니펫 역추적 → LLM 1회로 정의 작성. 근거 실측: 범위 밖 참조 보존율 23% vs 범위 안 92%.

**시사점**: 화수 몫으로 남는 축은 이것들과 직교하는 **retrieval/인덱스 + Skill.md 연동 + 주제 뷰**다. 아래가 그 분석.

## 2. 로컬 인덱스 기반 동적 retrieval — 실현성: 높음 (핵심 제안)

### 왜 이게 정확히 맞는 과녁인가 — 실측 근거

feat/compact의 QA 실측에서 **오답 18건 전원이 "정보 탈락(모름)"이었고 환각은 0건**이다 (prompt.ts v3.5 주석). 즉 압축의 손실 모드는 "틀리게 기억"이 아니라 "아예 잃음"이고, 잃은 것은 **원문 재조회로만 복구 가능**하다. retrieval은 보존율 92%의 나머지 8%를 겨냥하는, 손실 모드에 정확히 대응하는 장치다. "압축은 삭제가 아니라 접기"라는 기존 원칙(`/api/expand` 설계 사상)의 완성형이기도 하다.

### 무엇을 새로 만들어야 하나 — 사실상 하나

`GET /api/search?project=&q=` 엔드포인트:

```
buildForest → flattenTurns → labels 조인
→ 점수화: ① 식별자 정확 매치(파일명·CamelCase — identTokens 재사용, 가중 높게)
          ② 제목·요약 키워드 매치 ③ files 배열 매치 ④ 최신성 보정
→ 상위 N개 {id, ts, title, gist, files, sessionId} 반환
```

서드파티 0 방침 유지 가능 — BM25-라이트 점수화는 순수 JS 수십 줄. 기존 GET 핸들러들(`/api/labels`, `/api/mtime`)과 같은 패턴으로 붙는다.

### 한계를 솔직하게 — 그리고 왜 괜찮은가

임베딩 없이 한국어 **의미** 검색은 약하다. 이것이 괜찮은 이유는 호출자가 사람이 아니라 **LLM 에이전트**이기 때문이다: 쿼리 확장(동의어·영문 식별자로 여러 번 검색)을 에이전트가 알아서 하고, 코딩 세션 검색의 실질 키는 대부분 식별자(파일명·함수명)라 정확 매치가 강력하다. 부족하면 label 스키마에 검색 키워드 필드(`k` 배열)를 추가하는 확장 여지도 있다 — 캐시 해시 구조상 스키마 확장은 자연 재생성으로 흡수된다.

### "RAG처럼 사실성을 높인다"는 주장의 검증 방법

MS.LIM의 QA 방법론을 그대로 재사용해 **retrieval on/off A/B**를 돌리면 된다: 같은 130문항을 "패키지만" vs "패키지 + search/expand 허용" 두 조건으로. 보존율 92% → X%의 실측 한 장이 나오면 심사(8/27 마감) 스토리가 완성된다. 새 방법론 설계 비용 0.

## 3. Skill.md 연동 — 실현성: 높음, 차별화 최대

### 에이전트가 SKILL.md를 참조·호출하는 프로세스 (회의 조사 항목 답)

Claude Code 기준 (Codex도 유사한 AGENTS.md/skills 개념 수렴 중):

1. **배치**: `~/.claude/skills/<이름>/SKILL.md` (전역) 또는 프로젝트 `.claude/skills/<이름>/SKILL.md`. frontmatter에 `name`, `description` 필수.
2. **상시 로드는 한 줄뿐**: 시스템 프롬프트에는 스킬의 name+description 한 줄만 올라간다 (progressive disclosure — 컨텍스트 비용 최소).
3. **호출**: 사용자가 `/이름`으로 수동 호출하거나, **모델이 요청과 관련 있다고 판단하면 스스로 Skill 도구로 호출**한다. 이때 비로소 SKILL.md 본문 전체가 컨텍스트에 로드된다.
4. **실행**: 본문은 자연어 지시문이고, 에이전트는 그 지시대로 Bash(curl 등)·Read 등 도구를 실행한다. 스킬 폴더에 스크립트·참조 파일을 동봉해 본문에서 가리킬 수 있다.

우리 레포의 `.claude/commands/branchport.md`(슬래시 커맨드)와의 차이: 커맨드는 사용자가 수동으로 부르는 매크로, 스킬은 **에이전트가 필요할 때 자동으로 집어 드는 능력**이다. "유동적으로 활용"이라는 회의 표현에 부합하는 쪽은 스킬.

### 설계: `branchport-recall` 스킬 (레포에 동봉 배포)

```markdown
---
name: branchport-recall
description: 과거 Claude Code 세션에서 했던 작업·결정·에러를 검색해 원문을 인출한다.
  사용자가 "예전에/지난번에/그때 ~했던" 것을 물거나, compact 이후 잃은 맥락이 필요할 때 사용.
---
1. curl 'http://127.0.0.1:4300/api/search?project=<현재 프로젝트 dir명>&q=<키워드>'
   — 식별자(파일명·함수명)를 우선 키워드로. 결과가 빈약하면 다른 키워드로 재시도.
2. 유망한 턴은 curl '/api/expand?...&turn=<id>'로 원문을 가져와 답변 근거로 사용.
3. 서버가 안 떠 있으면(연결 거부) `node <레포>/dist/server.js` 기동 후 재시도.
```

- **배포**: 레포에 `skills/branchport-recall/SKILL.md`로 두고 README에 "폴더를 `~/.claude/skills/`로 복사" 한 줄 — "사람들이 쓸 수 있게 변환"이 곧 이 형태다.
- **보안 모델과의 정합**: 검색·expand는 GET이라 기존 로컬호스트 제한만으로 충분, 새 공격면 없음.
- **의미**: 이 스킬 하나로 BranchPort는 "지난 세션을 보는 도구"에서 **현재 세션의 에이전트가 과거를 인출하는 장기기억 백엔드**가 된다. compact로 잃은 맥락을 자기 로그에서 되찾는 도구는 아직 공개 사례가 드물어 대회 차별화 포인트로 유효 (평가지표 문서의 "Claude Code /compact 정량 평가 벤치마크는 없다" 관찰과 같은 맥락의 공백).

### LLM wiki 확장에 대해

labels+주제 요약을 마크다운 지식베이스로 export하는 것은 위 retrieval API 위에 뷰 하나 얹는 일이라 기술적으로 쉽다. 다만 8/27 전에는 스킬 경로가 같은 가치를 더 적은 비용으로 증명하므로 **후순위 제안**.

## 4. 세션 내 주제 식별/분기 뷰 — 실현성: 중간, 설계 주의 필요

- **입력이 이미 싸다**: 턴별 LLM 제목이 캐시에 있으므로, 제목 시퀀스만 claude -p 1회에 넣어 `{구간 경계, 주제명}` JSON을 받으면 된다. 원문을 다시 넣을 필요 없음 — 라벨 파이프라인(`LABEL_SCHEMA` 패턴)과 동일한 구조로 소구현 가능.
- **주의 — 기존 원칙과의 충돌 지점**: 실측(JSONL 19,833건 분석)상 로그에 의미 분기는 0.28%뿐, 주제 구조는 물리적으로 존재하지 않는다. 캡슐이 "확실한 신호(30분 공백·compact 경계)에서만 자른다"는 원칙으로 설계된 이유다 (기능내역 §3). LLM 주제 경계는 본질적으로 추측층이므로 **캡슐을 대체하지 말고 별도 토글("주제 렌즈")로** 얹어야 한다. 틀려도 비용이 "토글 끄기"가 되게.
- **재사용 연결**: 주제 구간은 그대로 ① 세션 셀렉터의 주제별 점프(= 회의의 "네비게이션 바" 요구를 자연 해소) ② `/api/search`의 필터 ③ "주제별 개별 요약" = 그 구간을 기존 `/api/compact`에 넘기는 것과 동치.
- **캡슐 LLM 제목**(회의 메모 "캡슐 — LLM 기반으로도 생성?"): 구간 첫 턴 제목을 대표로 쓰는 현 한계(기능내역 §알려진 한계)에 대한 답으로, 구간 내 제목들을 12자로 재요약하는 배치를 라벨 루프에 편승시키면 된다. 소품.

## 6. 심화 조사 (8/9 저녁 추가) — 스킬 정밀 스펙 · 선행 기술 지형 · 훅 발견

### 6.1 스킬 스펙 — 공식 문서 확인 결과 (code.claude.com/docs/en/skills)

- 위치 3단: 개인 `~/.claude/skills/<이름>/SKILL.md` · **프로젝트 `.claude/skills/<이름>/SKILL.md`** · 플러그인. **프로젝트 스킬은 레포를 연 사람에게 자동 로드**(신뢰 다이얼로그 1회) — "폴더 복사" 안내조차 필요 없음. 우리 레포의 `.claude/commands/branchport.md`도 같은 체계(커맨드는 스킬로 통합됨).
- frontmatter에서 우리에게 유효한 필드: `description`(+`when_to_use`, 합산 1,536자 컷 — 트리거 문구를 앞에), **`allowed-tools`** — 예: `Bash(curl http://127.0.0.1:4300/*)`를 선승인해 스킬 발동 턴의 권한 프롬프트 제거. `disable-model-invocation`은 기본 false = 모델 자동 발동이 기본.
- 스킬 폴더에 스크립트·참조 파일 동봉 가능, 파일 변경은 세션 재시작 없이 반영.

### 6.2 선행 기술 지형 — "아무도 안 한다"는 틀렸고, 그래서 포지셔닝을 고쳐야 함

| 선행 | 방식 | 우리와의 거리 |
| --- | --- | --- |
| **claude-mem** (오픈소스, ~84k★) | 훅으로 세션 중 관찰을 **상시 캡처**→LLM 압축→차기 세션 주입. search→timeline→get 3층 점진 공개 | 우리 search→expand 제안과 **동형 구조** — 설계 방향의 외부 검증인 동시에, "메모리 자체"로는 선점됨 |
| **memsearch** (Zilliz) | 턴 요약을 마크다운+Milvus Lite 벡터 인덱스. `transcript --turn <uuid>`로 **CC JSONL 원문 인출까지 있음** | `/api/expand`와 가장 근접한 선행 |
| mem0 · Letta · Zep | 인프라형 메모리 레이어(계층 승격 / 시간 지식그래프 / 에이전트 자율 메모리) | 클라우드/DB 지향 — 우리 지향과 다른 층 |

**수정된 정직한 차별점** (이것만 주장할 것):
1. **소급(retroactive)**: 선행들은 설치 시점부터 캡처. 우리는 디스크에 이미 있는 전체 JSONL을 채굴 — 설치 전 과거까지 전부 검색됨, 캡처 훅·DB 불필요.
2. **시각적 착지**: 검색 결과를 텍스트 목록이 아니라 **트리 위 위치로** 반환(하이라이트→워프). 선행 중 시각화와 결합한 사례 없음 — 시각화 도구만 가능한 UX.
3. **의존성 0 완전 로컬**: Milvus Lite조차 없이. (벡터는 Ollama 감지 시에만 켜지는 선택 층으로 — §6.4)
4. **갈래 대화와 결합**: 검색으로 찾은 과거 시점의 AI와 그 자리에서 대화 — 유일 기능.

### 6.3 훅 발견 — "compact 보험" (창의적 확장 1순위 후보)

공식 훅 목록에 **`PreCompact`**(컴팩션 직전 실행, 차단도 가능)과 `SessionStart`(additionalContext 주입 가능), `PostCompact`가 확인됨. 조합하면:

> PreCompact 훅 → BranchPort 서버에 현 세션 자동 압축 요청(기존 `/api/compact` 재사용, 앵커 포함 패키지 저장) → compact 이후 세션에 "잃은 맥락은 branchport-recall로 검색·인출 가능 + 패키지 경로" 한 줄 주입.

- **의미**: Claude Code가 맥락을 버리기 직전에 자동 스냅샷이 남고, 버린 후에는 인출 통로가 자동 안내됨. 상시 캡처(claude-mem)와 달리 **손실 이벤트에만 개입**하는 소급형 보험 — 선행 없음.
- 비용: 훅 스크립트 ~수십 줄 + 서버에 자동 압축 진입점 1개. 압축 파이프라인은 전부 기존 코드.
- 미확정: compact 직후 주입 지점(PostCompact의 주입 지원 여부 vs SessionStart의 compact 매처)은 구현 시 실측 확인 필요 — 여기만 추측임.

### 6.4 검색 품질 로드맵 (요즘 기술의 현실적 적용)

- 1단계(대회 범위): BM25-라이트 + identTokens 정확 매치, 순수 JS — 의존성 0 유지. **(8/10 구현 완료)**
- 2단계(선택 층): **Ollama가 로컬에 있으면** nomic-embed-text로 요약문 임베딩→해시 키로 캐시, BM25와 RRF(reciprocal rank fusion) 융합. 없으면 조용히 1단계로 폴백 — 하이브리드+폴백은 2026 로컬 검색의 표준 패턴. sqlite-vec는 네이티브 모듈이라 의존성 0 방침 위반 — 채택 금지.
- **자동 다운로드 옵션 판정 (8/12)**: transformers.js(WASM ONNX, 첫 실행에 모델 자동 다운로드)는 기술적으로 실재하나 ① npm 의존성 수십 개 — "서드파티 0" 방침 정면 위반이라 **팀 결정 사안** ② 한국어 가능 다국어 모델 ~120MB, 첫 실행 인터넷 필요 — "완전 로컬" 서사 흠집 ③ 이 머신에 Ollama 부재로 Ollama 경로는 현재 e2e 검증 불가. **권고 순서: QA A/B로 현 키워드+그래프의 보존율 기여를 먼저 측정 → 개념어 실패가 숫자로 아프면 회의에서 Ollama형(방침 유지) vs transformers.js(방침 변경) 결정 → 결정된 환경에서 구현·검증** (설계는 확정돼 있어 하루 작업).

### 6.5 LLM 위키 재평가 (질문에 대한 답)

- **자동 생성 도시에(dossier)로는 가능하고 저렴**: 주제 렌즈 구간별 요약 + 턴 앵커 링크를 마크다운으로 export — 검색 API 위의 뷰 하나, 신선도는 해시 캐시가 해결.
- **수동 큐레이션 위키(Karpathy형)로는 비추천**: 유지 비용이 사람에게 전가되고, 8/27 전 가치 증명이 어려움. 그리고 그 역할의 절반은 검색+expand가 이미 함.
- 순서 불변: search/skill → compact 보험 → 주제 렌즈 → 도시에 export.

## 7. 그래프RAG 적용 검증 (8/9 밤 추가) — "미니그래프→메가그래프" 구상의 엄밀 평가

### 7.1 결론 먼저

- **정통 GraphRAG(노드별 LLM 엔티티 추출→그래프 병합→커뮤니티 요약)은 보류가 옳다.** 근거는 "비용이 크다"보다 구조적이다(§7.2).
- **그러나 그 목표(연결 기반 회수)는 포기할 필요가 없다** — 우리 로그는 그래프를 **이미 갖고 있어서**, LLM 추출 없이 결정론적으로 그래프 검색이 된다(§7.3). 이는 2026년 흐름(LazyGraphRAG: 인덱싱 때 LLM 배제, 질의 때만 사용 — 인덱싱 비용 정통 대비 0.1%)과 정확히 같은 방향이고, 우리는 그래프 구축조차 공짜라는 점에서 더 유리하다.

### 7.2 정통 GraphRAG를 보류해야 하는 구조적 이유 3가지

1. **한계효용**: LLM이 추출할 엔티티의 대부분(파일명·함수명·에러명)은 이미 turn 메타(`files`)와 `identTokens()`(파일명·CamelCase·ALL_CAPS·snake_case)로 **기계 추출된다**. LLM 추출이 새로 주는 것은 소프트 개념·인물 관계인데, 코딩 로그 질의에서 가치가 낮다.
2. **증분 갱신**: 세션 로그는 계속 자란다. 원본 변경 시 그래프 재계산이 GraphRAG 계열의 공인된 약점(2026 실무 보고들 공통) — 상시 자라는 코퍼스와 최악의 궁합.
3. **추출 품질**: 대화 로그의 관계 추출은 노이즈가 크고(가설↔확정 구분 등), feat/compact 감사에서 확인된 오귀속·인과 단정 오류가 그래프에 굳는 위험이 있다.

비용 자체는 라벨링과 같은 배치 방식이면 자릿수는 견딜 만하다 — 즉 "비용이 많이 들겠지"는 절반만 맞고, 진짜 문제는 위 3가지.

### 7.3 채택안: 결정론 그래프 + 질의 시점 확장 (구현 ~100줄)

로그가 이미 갖고 있는 엣지: 턴↔파일(`files`), 턴↔식별자(identTokens를 턴 원문에 적용 — LLM 불필요, 전 턴 커버), 턴↔세션·포크(parentUuid·접합), 턴↔주제구간(주제 렌즈), 턴↔에러(hasError). 물질화 인덱스에 **역인덱스(식별자→턴id들)**를 포함하면 그래프는 끝.

`/api/search` 2단계 검색:
1. 키워드/식별자 매치로 시드 턴 확보
2. **그래프 확장**: 시드의 ①같은 파일을 만진 턴 ②조상 경로 ③포크 형제 ④같은 주제 구간 → 후보 확대 → 점수 융합(직접 매치 > 1-hop)

효용의 실례(가설): "CORS 에러 해결" 질의 — 해결 턴 요약이 "프록시 설정 수정"으로 적혀 키워드 미스여도, "CORS"로 잡힌 에러 턴에서 같은 파일 엣지로 해결 턴이 회수됨. **가설이므로 QA A/B(기존 방법론)에 "연결 회수형 질문" 유형을 넣어 검증할 것.**

커뮤니티 요약의 역할은 주제 렌즈 구간 요약이 정확히 대신한다(전역 질문용). 미니그래프→메가그래프가 진짜 필요해지는 조건: 멀티 프로젝트 횡단 검색, 수만 턴 규모, 관계 질문 수요 실측 — 그 전엔 과설계이며, 그때는 LightRAG류 증분 방식부터 검토.

### 7.4 검색용 디스크립션 보강 (노드별 요약을 더 구체적으로?)

직감은 옳다 — 표시용 요약(g, 사람이 읽는 100자)과 검색용 표현은 목적이 다르다. 다만 순서가 중요하다:

1. **공짜부터**: 검색 키의 대부분(파일·식별자·에러명)은 인덱스 빌드 때 턴 원문에 identTokens를 돌려 기계 확보 — LLM·재라벨링 불필요, 기존 턴 전부 커버.
2. **LLM 보강은 차액만**: LABEL_SCHEMA에 검색 키워드 배열 `k`(동의어·영한 대응·개념어) 추가. 단 해시는 내용 기반이라 **기존 캐시는 자동 재생성 안 됨** — 신규 라벨부터 점진 보강임을 전제할 것.
3. **의미 갭은 임베딩 선택층**(§6.4 Ollama 폴백)이 담당.

### 7.5 압축과 인덱스의 관계 (정확한 그림)

압축 자체의 손실률은 프롬프트의 몫(MS.LIM, 92%)이고, 인덱스는 압축을 "더 잘하게" 하는 게 아니라 **손실을 소비 시점에 복구**하게 한다. 3층 방어: ①요약 개선(압축 시점, feat/compact) ②앵커+용어부록 동봉(패키지 안, 이미 있음) ③검색·인출(소비 시점, 우리). 추가 소기능: **압축 패키지(pkg-*.json)도 인덱스에 등록**해 "과거에 만든 패키지 검색"까지 가능하게 — 몇 줄이면 된다.

위키(도시에)는 별도 그래프를 만드는 게 아니라 **같은 결정론 그래프의 사람용 투영**이다: 주제 페이지(주제 구간), 파일 페이지(그 파일을 만진 턴 연대기 — LLM 없이 생성 가능), 에러 페이지(hasError 턴+해결 턴), 문장마다 턴 앵커. 하나의 구조, 세 개의 뷰: 트리(시간·구조) · 검색(질의) · 위키(브라우징).

## 8. 결정론 그래프 품질 실측 (8/9 밤, 실데이터)

측정: main의 dist 파서로 실제 로그를 파싱, 턴↔파일·턴↔식별자(identTokens 규칙 재현, df≤30% 필터) 엣지의 연결성·회수력 측정. 대상: 오픈소스프로젝트 프로젝트(254턴).

| 지표 | 값 | 해석 |
| --- | --- | --- |
| 파일 만진 턴 | 42% (고유 파일 109) | 파일 엣지의 원료 충분 |
| 유효 식별자 | 158개 | 식별자 엣지 원료 충분 |
| 이웃 수 중앙값 | 18 (평균 28) | 그래프가 실재하고 조밀함 |
| 고립 턴 | 파일 엣지만: 60% → 식별자 추가: **28%** | 대화·탐색 턴은 여전히 고립 — 세션 인접 엣지 추가 필요(추가 시 0%) |
| 1-hop 확장 | 시드 19턴 → **156턴 (전체의 61%)** | **핵심 발견: 단순 1-hop은 과확장으로 무용** |

**결론**: 원료 품질은 좋다(결정론 엣지만으로 중앙값 18 이웃). 그러나 이분법 확장(hop)은 정밀도가 무너진다 — 흔한 파일(index.html은 19턴이 만짐)이 허브가 되어 전체를 끌어오기 때문. 따라서 **가중 확산이 필수**: 엣지 가중 1/√df(흔한 파일·토큰일수록 약하게) + Personalized PageRank(시드에서 확산, 점수 감쇠). 254노드 그래프에서 PPR power-iteration은 밀리초 단위 — 순수 JS로 충분.

이 설계는 2025–26 그래프RAG 계보의 정확한 적용이다: LazyGraphRAG(인덱싱 LLM 제거) → LiteSemRAG(LLM-free 그래프 구축, 2026.4) → HippoRAG 2·Fast GraphRAG(**PPR 시드 확산**이 검색 코어). 우리 차이는 그래프 구축조차 0원(로그가 구조를 이미 가짐)이라는 것. 명칭 제안: **"로그 네이티브 그래프 + PPR 확산"**.

## 11. 설계 판정 2건 (8/10 밤) — 주제 구분 방식 · 압축 시 관련 내용 동봉

**주제 구분(주제 렌즈)의 방식 — "그래프로?"에 대한 답: 문제를 둘로 쪼개면 답이 갈린다.**
- **연속 구간 경계**(세션 안에서 주제가 바뀌는 지점): 그래프 부적합 — 커뮤니티 검출은 시간 연속성을 무시함. 2025–26 실무 표준은 ① LLM에게 경계 삽입을 시키는 방식(LumberChunker 패턴 — 문단 사이 주제 전환점을 LLM이 찍음, DCG@20 +7.4%) ② 임베딩 인접 유사도 골짜기 검출. **우리 최적해 = LumberChunker 패턴을 "턴 제목+요약 시퀀스"에 적용** — 원문 대신 이미 캐시된 라벨을 입력하므로 세션당 LLM 1회, 결과는 세션 내용 해시로 캐시. 대화 이력을 주제 구간으로 잘라 구간 단위로 기억·검색하는 것이 턴/세션 단위보다 낫다는 선행 연구도 확보(SeCom, arXiv 2502.05589).
- **주제 재방문 연결**(떨어진 구간이 같은 주제): 여기가 그래프의 자리 — 구간 간 공유 식별자·파일 co-occurrence로 결정론 교차 링크(LLM 0회). 기능내역 "이식 전" 항목이던 교차 링크의 구현 경로.
- 전제 유지: 경계는 추측층이므로 캡슐 대체가 아닌 토글 렌즈(§4).

**압축 시 리트리버로 관련 내용 동봉 — 화수 제안 판정: 방향 맞음, 형태 조정 필요.**
