# 조사: 압축 범위 밖에서 정의된 용어의 사전(단어사전) 첨부 방안

> 2026-08-08 작성. 병렬 조사 2갈래(① Claude Code Skills 메커니즘·도구 생태계 실태, ② 에이전트 메모리·용어 추출 선행연구) + 내부 문서 대조([조사_GLOSSARY_용어정립_방법.md](../오픈소스/조사_GLOSSARY_용어정립_방법.md), [개념_ReSum.md](../오픈소스/개념_ReSum.md)).
>
> 발단: compact로 지정한 범위 **밖**(세션 초반)에 핵심 용어·약어의 정의가 있고 범위 **안**에서는 그 용어가 정의 없이 재사용되는 경우, 패키지를 받은 새 세션이 용어를 해석할 수 없다. 해법으로 "SKILL.md를 이용해 대화 중 단어사전을 축적"하는 아이디어가 나와 실현 가능성을 조사했다.

---

## 결론 요약

1. **"SKILL.md로 대화 중 사전을 자율 축적"은 신뢰할 수 없는 설계다** — Anthropic 공식 문서가 명시적으로 부정한다. 스킬은 ①발동 자체가 모델의 관련성 판단에 의존하고, ②한 번 로드되면 재실행되지 않으며("does not re-read the skill file on later turns"), ③auto-compaction 시 스킬당 5k·합산 25k 토큰 예산으로 재부착되어 호출 빈도 낮은 스킬부터 드롭된다 — **하필 압축이 일어나는 순간에 사전 유지 지시가 사라질 수 있다**. 공식 문서 스스로 "매 턴 강제가 필요하면 스킬이 아니라 hook을 쓰라"고 안내한다.
2. **조사한 모든 기존 도구가 "메인 에이전트에게 곁다리로 알아서 기록시키기" 패턴을 쓰지 않는다.** 신뢰 가능한 구현은 전부 (a) 결정적 비-모델 트리거(hook·명시적 도구 호출), (b) 명시적 사용자 커맨드/승인(Cline "update memory bank", Devin Knowledge), (c) 메인 대화와 **분리된 관찰·추출 프로세스**(Cursor Memories의 백그라운드 모델, ChatGPT 메모리의 별도 fact-extraction LLM) 중 하나다.
3. **BranchPort는 애초에 실시간 축적이 필요 없다.** 우리는 완료된 jsonl을 사후에 읽는 도구라, compact 시점에 범위 밖 조상 턴을 전부 볼 수 있다 — "라이브 준수 문제"를 구조적으로 회피하는 **compact 시점 사후 추출**이 정공법이다. 선행연구도 같은 방향을 가리킨다(사후 일괄 > 매 턴 실시간, 아래 §3).
4. 권장 파이프라인: **범위 안 후보 추출(규칙 pre-filter + LLM) → 범위 안에서 정의 여부 판별 → 미정의 용어를 조상 턴에서 역추적 → 1\~2문장 정의 생성 → 패키지에 "용어 부록" 섹션 첨부**(앵커 연결로 /expand 연계). 저장은 그래프 DB가 아니라 평면 "용어→정의" 맵이면 충분하다.
5. **"정의는 앞에, 참조는 뒤에" 패턴을 직접 재는 벤치마크는 존재하지 않는다** — QA 보존율 파이프라인을 확장해 "범위 밖 정의 질문" 트랙을 만들면 평가 공백을 메우는 자체 기여가 된다.

## 1. 문제 정의와 현재 장치의 한계

- 현재 compact 패키지가 범위 밖 맥락을 다루는 장치는 셋: **계보**(이 구간이 어디서 갈라졌는지), **조상 턴 개수**("같은 세션 조상 N개 미포함 — /expand로 조회"), **원문 앵커**. 전부 "**필요하면 원문을 조회하라**"는 지연 해석(lazy lookup) 설계이고, 정의 자체를 실어주지 않는다.
- 이 설계의 공백: 받은 쪽이 **자기가 모르는 용어인지조차 모를 수 있다**(모르는 것을 모름). 용어가 요약 문장 안에 자연스럽게 박혀 있으면 조회할 계기가 없다. QA 보존율의 "정직한 누락"(모름) 서사가 성립하려면, 최소한 "이 단어는 범위 밖에서 정의됐다"는 신호가 패키지에 있어야 한다.
- 실측 근거(간접): LongMemEval에서 상용 챗봇들이 세션 경계를 넘는 정보 유지에 최대 30%p 정확도 하락([arXiv:2410.10813](https://arxiv.org/abs/2410.10813)). 추출 요약의 "dangling anaphora"(선행사가 요약 밖이라 대용 표현이 해석 불능)는 1990년대부터 알려진 고전 문제이고, 제안된 해법도 "생성 후 검증" 후처리다([Two uses of anaphora resolution in summarization](https://www.sciencedirect.com/science/article/abs/pii/S0306457307000428)).

**설계 패턴 결론**: 압축 대상 범위가 **사후에** 정해지는 우리 상황에서는 "매 턴 실시간"의 이점이 없다. 세션이 끝나기 전엔 무엇이 나중에 참조될지 모르므로 임계값 설계도 어렵다. **compact 시점 사후 일괄 추출이 가장 적합** — 실시간 오버헤드 0, 라이브 준수 문제 회피, 범위가 확정된 뒤라 "범위 밖 정의 + 범위 안 참조" 교집합을 정확히 계산할 수 있다.

### 용어 판별 방법

- LLM 기반 자동 용어 추출(ATE)이 2024\~2025 활발: [LlamATE](https://benjamins.com/catalog/term.00082.tra), [Syntactic-Retrieval ATE (ACL 2025 Findings)](https://arxiv.org/pdf/2506.21222) — **규칙(통사) 신호 + LLM 결합이 순수 LLM·순수 통계 양쪽을 이긴다**.
- GlossaGen: 문서에서 용어·정의를 추출해 용어집 생성 — 우리 목적과 가장 유사한 선례. 평면 "용어→정의" 맵이면 충분하다는 근거.
- 비-LLM 베이스라인(TF-IDF/RAKE/YAKE)은 빈도 통계 기반이라 **한 번만 정의된 약어(우리 핵심 케이스)를 놓친다**. 백틱·PascalCase·전대문자 약어 휴리스틱은 정밀도 높고 재현율 낮음 → **1차 후보 필터로만** 사용.

## 5. 권장 설계 스케치 (옵션 C)

```
[범위 확정] ──▶ ① 후보 추출: 범위 안 텍스트에서 규칙 필터
                  (백틱 토큰·PascalCase/camelCase·전대문자 약어·고유명사)
          ──▶ ② 범위 안 정의 여부 판별 — 정의가 범위 안에 있으면 제외
                  (요약이 이미 담음: 기존 v3.5 규칙의 영역)
          ──▶ ③ 잔여 후보를 조상 턴(priorSameSession + fork 계보)에서 역추적
                  — 첫 등장·정의 문맥 스니펫 수집 (기계 검색, LLM 불요)
          ──▶ ④ LLM 1회: 스니펫 근거로 용어당 1~2문장 정의 생성
                  (GLOSSARY 방법론 차용: 정의 2문장 이내·식별자 앵커·추측 금지,
                   근거 스니펫 없는 용어는 "정의 미발견 — 앵커 참조"로 표기)
          ──▶ ⑤ 패키지에 "## 용어 부록 (범위 밖 정의)" 섹션 첨부
                  — 각 항목에 정의 위치 앵커(턴 id) 연결 → /expand로 원문 검증 가능
```

- **위상**: 사실층과 같은 "구조 보증" 계열이되, 정의 문장 생성에만 LLM이 개입하는 혼합층. ②의 인젝션 방어·evidence 규칙은 기존 compact 프롬프트 원칙을 그대로 상속.
- **비용**: 조상 턴 전체를 LLM에 넣지 않는 것이 핵심 — ③이 기계 검색(문자열 매칭)으로 스니펫만 추리므로, ④의 입력은 용어 수 × 스니펫 길이로 유계. compact 1회당 추가 호출 1회(haiku급도 후보).
- **실패 모드 처리**: 조상에서도 정의를 못 찾은 용어는 부록에 "미발견"으로 명시(모르는 것을 아는 척하지 않기 — QA 실측의 "정직한 누락" 서사 유지).

## 6. 평가 방법 제안 — "범위 밖 정의" QA 트랙

기존 QA 보존율 파이프라인(지표 문서 §2)을 재사용한 통제 실험:

1. 조상 턴 구간에서만 정의되고 범위 안에서 재참조되는 용어를 골라 **"범위 밖 정의 질문"** 생성 ("X는 무엇을 가리키는가?", "X의 포트/값은?")
2. 부록 없는 패키지 vs 부록 있는 패키지로 답변 비교 — 부록의 기여를 %p로 직접 측정
3. 무맥락 대조로 찍기 보정 (기존 설계 그대로)

이 패턴을 직접 재는 공개 벤치마크가 없으므로(§3, LongMemEval knowledge-update가 최근접 대리), 자체 평가셋 자체가 보고서의 기여점이 된다. 데이터 후보: compact 경계가 실재하는 11세션(builtin-compare에서 확보)은 "경계 이전=조상, 이후=범위" 구도가 이미 있다.

"정의는 조상 구간에만, 참조는 선택 구간에" 조건의 질문(세션당 최대 8개, 억지 생성 금지)을 던졌다.
턴 4개 미만·조상 구간 2k자 미만 세션은 제외 → 13개 중 7개 측정(질문 48개).

| 측정값                                                      | 결과                                       |
| ----------------------------------------------------------- | ------------------------------------------ |
| **OOR 보존율**                                        | **11/48 (23%)** — 세션별 0/8 \~ 5/8 |
| 범위 안 QA 보존율(참조: 지표 문서 §2 v3.5)                 | 92%                                        |
| **격차 = 문제 크기**                                  | **약 69%p**                          |
| 무맥락 대조                                                 | 0/48 (질문 필터 유효)                      |
| 교차 토큰율(결정론): 선택 구간 식별자 중 조상 구간에도 등장 | 249/794 (31%, 세션별 18\~64%)              |
| 비용                                                        | $5.5 (compact 7회 + QA 채점)               |

해석:

- **문제는 실재하고 크다**: 경계 넘는 참조 질문의 77%를 현재 패키지가 못 받는다. "This is an
  excerpt" 규칙(범위 밖 추측 금지)이 의도대로 작동하는 정직한 결과이지만, 받는 쪽 입장에서는
  범위 안에서 쓰이는 용어의 정의가 통째로 빠져 있는 상태다. 용어 부록(옵션 C)이 겨냥할 공간이
  최대 69%p로 실측 확정됐다.
- **23%는 어떻게 살아남았나**: 정답 사례를 보면 조상에서 정의된 작업(Task #2\~#6 등)이 선택
  구간에서 실제로 진행되어, 범위 안 활동 서술로부터 정의가 간접 복원된 경우다 — 즉 "범위 안에서
  재정의된 것"이지 범위 밖 정보가 새어든 게 아니다.
- **교차 토큰율 31%**은 선택 구간 식별자 3개 중 1개가 조상 구간에서 이미 등장했다는 뜻 —
  후보 추출 규모(부록 파이프라인 ①\~③의 입력 크기)의 상한 통계.
- **부산물 — 채점자 붕괴 1건과 결정론 가드**: 한 세션에서 채점자가 "모름"↔"모름" 쌍 8건을 전원
  정답 처리하는 붕괴가 발생(무맥락 8/8이라는 불가능한 수치로 즉시 발각 — 무맥락 대조의 부수
  효용). "모름" 답변을 채점자 판정과 무관하게 오답 처리하는 결정론 가드를 스크립트에 추가해
  재집계했다. 지표 문서의 "채점 표본 사람 검수 필요" 우려가 실측으로 확인된 사례이며, 같은
  가드를 qa-preservation.mjs에도 이식할 가치가 있다.

한계: 7세션·48문항의 파일럿 규모. 절반 분할은 인위적 경계라 실사용(사용자가 고른 범위)과
다를 수 있고, 질문 생성이 "조상에만 정의 존재"를 보장하는 필터도 LLM 판단이다(무맥락 0으로
간접 검증). 다음 단계는 부록 구현 후 **동일 질문지 재채점**(고정 벤치마크 관례)으로 개선 폭을
직접 재는 것. → 아래 §7.1에서 수행.

### 7.1 용어 부록 구현 후 재채점 (2026-08-08)

§5 설계를 구현했다: `src/glossary.ts`(후보 추출·조상 스니펫 역추적·정의 프롬프트) +
`src/server.ts` compact 파이프라인 통합(md "## 용어 부록" 섹션·json `glossary` 필드·
`glossary:false` 비활성 파라미터). **동일 질문지 48문항·동일 무맥락 답변**(캐시 이관)으로
부록 있는 패키지를 재채점했다. 원자료: `batch-results/oor-terms-glossary/`.

|            | 부록 없음(v1) | 부록 있음(v2)                                            |
| ---------- | ------------- | -------------------------------------------------------- |
| OOR 보존율 | 11/48 (23%)   | **16/48 (33%)**                                    |
| 세션별     | 5,0,0,1,0,2,3 | 5,**5**,0,0,0,**3**,3                        |
| 부록 생성  | —            | 7세션 전부 성공, 후보 141 → 항목 49, 부록 비용 합 $0.84 |

**+10%p — 그러나 개선은 부록의 적중 영역에 정확히 집중됐다**:

- **성공 패턴(kr-08993363, 0→5/8)**: ALL_CAPS 약어(TGIP·RTS·TPI·FSS·WSD)가 조상 구간에서
  명시적으로 정의된 세션 — 부록이 5문항을 직격. **"식별자형 용어 + 정의형 질문"이 부록의
  설계 영역이고, 거기서는 실증적으로 작동한다.** 부록 정의에 수치가 실린 경우
  (kr-995c0a21의 `HIGH_RES_AREA_THRESHOLD` — 1_000_000) 값 질문도 맞혔다(수치 보존
  규칙과 동일한 원리).
- **잔여 오답의 주성분은 "값·사건 회상형" 질문**: 포트 번호·라인 수·파일 크기·버전 문자열·
  에러 원인·수정 전 문구 같은, 조상 구간의 **속성값·사건**을 묻는 질문(48문항 중 약 3/4).
  kr-2b3756eb는 8문항 중 6문항에서 용어가 부록에 있었는데도 오답 — 부록은 "무엇인가"를
  답하지, "그때 값이 얼마였나"를 답하지 않는다. **이 영역은 사전의 원리적 범위 밖이며
  /expand(원문 조회)의 영역** — 부록의 "정의 위치 앵커"가 그 조회 진입점 역할을 한다.
- **항목 0개 세션 3개도 규칙대로의 동작**: 생성 실패가 아니라(비용 발생·에러 없음 확인)
  스니펫이 정의를 담지 않아 모델이 전부 건너뛴 것 — 추측 금지 규칙이 지켜짐(환각 0 유지).
- 개선 여지 2건: ① 후보 추출이 라틴 식별자 전용이라 **한국어 개념어**("의사결정 중립 원칙" 등)를
  못 잡는다 — LLM 후보 추출 병행 검토. ② 용어당 스니펫 1개(첫 등장)만 제공 — 첫 등장이
  정의 지점이 아닐 수 있어 다중 스니펫 검토.

**결론**: 부록은 정의형 손실을 실증적으로 회복하고(적중 세션 0→63%), 나머지 격차는 사전이
아니라 원문 조회 계층의 몫임이 실측으로 분리됐다. 보고서 서사: "정의는 부록이, 값·사건은
앵커+/expand가" — 무손실 계층 설계와 정합.

### 7.2 개선 반복 1회 — v3 (2026-08-08)

§7.1의 개선 여지 2건 + 수치 규칙을 구현하고 **같은 48문항으로 3차 채점**했다.
변경: ① `phraseTokens` — 인용구(따옴표·백틱 안 2\~30자)와 개념 접미사("\~원칙/규칙/전략/방식"류)
한국어 명사구를 후보에 추가, ② 용어당 스니펫 2개(서로 다른 조상 턴), ③ 정의 프롬프트에
"스니펫이 용어에 결부한 구체 값(수치·포트·크기·경로·문구)은 verbatim 포함" 규칙.
원자료: `batch-results/oor-terms-glossary2/`.

|                 | v1(부록 없음) | v2(부록 초판) | **v3(개선판)**  |
| --------------- | ------------- | ------------- | --------------------- |
| OOR 보존율      | 11/48 (23%)   | 16/48 (33%)   | **19/48 (40%)** |
| 부록 항목 합    | —            | 49            | 96                    |
| 회귀(상실 문항) | —            | 1             | **0**           |

**개선분 +3의 출처가 전부 의도한 메커니즘으로 역추적된다**:

- kr-08993363 +1: "Phase 1 MVP 원안 범위" — **인용구 추출(①)**이 라우트 경로들(`/overview`,
  `/demo`, `/app/runs/:run_id`)을 후보로 잡아 부록 정의가 범위 값을 실어 날랐다.
- kr-2b3756eb +2: "performance-optimization.md 출처"(abseil.io URL)와 "system-rules.md 파일
  크기"(13129 bytes) — **수치 verbatim 규칙(③)**이 §7.1에서 "사전의 원리 밖"으로 분류했던
  값 질문 일부를 정의 문장 안으로 끌어들였다. 값·사건형의 경계는 고정이 아니라 "정의에
  값을 얼마나 실을 것인가"의 설계 변수임이 확인됨.
- v2에서 정답이던 문항의 상실 0 — 개선이 순증.

남은 오답 29건은 여전히 조상 구간의 사건 경위·세부 수치(에러 원인·셀렉터·수정 전 문구 등)로,
스니펫에 정의로 결부되지 않는 사실들 — /expand 계층의 몫. 특이 사항 1건: kr-995c0a21에서
부록이 후보 36 → 항목 0으로 나왔다(v2에선 12개. QA는 3/5 유지). 생성 호출은 성공했으므로
전부-스킵 혹은 출력 절단 추정 — compact 본체처럼 **빈 결과 1회 재시도** 가드가 다음 개선 후보.
(→ 이후 구현 완료: server.ts, 명시적 `[]`는 전부-스킵으로 존중하고 그 외 항목 0만 재시도)

### 7.3 부록 비용과 모델 라우팅 실측 (2026-08-09)

**비용 실측(v3·sonnet)**: 부록 호출은 세션당 평균 **$0.152**(입력 ~33.5k·출력 ~4.9k 토큰,
$0.09\~0.25) — compact 본체 평균($0.132)과 맞먹어, 부록을 켜면 compact 1회 비용이 약 2.1배가
된다. 입력 지배 구조(후보 최대 36개 × 조상 스니펫 2개, 한국어·코드 혼합의 높은 토큰 밀도).
§4.2 순절감 원칙에 따라 보고서의 비용 주장 시 이 부록 비용도 차감 항목에 포함할 것
(meta에 별도 계측됨).

**haiku 라우팅 실험**(`glossaryModel` 파라미터 신설, compact는 sonnet 유지, 동일 48문항):

| | sonnet 부록(v3) | haiku 부록 |
|---|---|---|
| OOR 보존율 | 19/48 (40%) | 15/48 (31%) |
| 부록 비용/세션 | $0.152 | **$0.064 (−58%)** |
| 부록 항목 수 합 | 96 | 90 (세션별 급감 있음: 11→5, 7→2) |

문항 단위 귀속(하락 4건): **3건이 haiku 부록 품질** — 항목 누락(인용구 라우트 항목 탈락)과
정의의 핵심 값 누락(수치 verbatim 규칙 미준수 — haiku의 QA 보존율 열세와 동일 패턴),
1건은 요약층 재생성 노이즈. 교란 요인: 이 실험은 v3.6 빌드(언어 결정론 지시)라 v3과 요약층
조건이 다르다 — 문항 단위 비교로 보정했다.

**결론**: 기본값은 sonnet 유지. `glossaryModel: 'haiku'`는 비용 민감 시의 옵션으로 남긴다
(−58% 비용에 보존율 −9%p) — §3.5 비용-품질 frontier의 부록판 실측 2점.

## 8. 발단 아이디어(SKILL.md)의 자리

실시간 축적 용도로는 부적합하지만, 스킬이 유효한 지점이 둘 있다:

- **받는 쪽 스킬**: 패키지를 새 세션에 붙일 때 "용어 부록을 먼저 읽고, 미발견 용어는 /expand로 조회하라"는 소비 규약을 스킬/커맨드로 제공 — 1회성 명시 호출이라 신뢰성 문제가 없다.
- **명시적 커맨드형 사전**: 사용자가 원할 때 `/glossary` 식으로 호출해 현재까지의 세션에서 사전을 뽑는 기능 — Cline "update memory bank"와 같은 명시 트리거 패턴. 단, 옵션 C가 있으면 필수는 아니다.
