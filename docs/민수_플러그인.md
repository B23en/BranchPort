# 플러그인에서 로컬 웹페이지 launch + 링크 제공이 가능한가 (Node.js 기반) + 의존성

---

## 1. "로컬 웹페이지 launch + 링크 제공" — 가능 여부

### 원리

MCP 서버는 **Claude Code가 띄우는 그냥 로컬 프로세스**다. stdio로 Claude와 대화할 뿐, 그 안에서 무엇을 하든 자유다 — HTTP 서버를 띄우든, 브라우저를 열든, 파일을 읽든.

```
Claude Code ──stdio(JSON-RPC)──> MCP 서버 프로세스
                                      ├── 백그라운드 스레드: HTTP 서버 (127.0.0.1:임의포트)
                                      └── 브라우저 실행 → 그 URL 오픈
                                          ↑ 사용자는 별도 탭에서 캔버스를 봄
```

`/tree` 호출 → 도구가 URL 문자열을 반환 → Claude가 그 URL을 응답에 출력 → **터미널에서 클릭 가능**. 브라우저 자동 오픈이 실패해도(헤드리스·WSL·SSH) URL만 있으면 사용자가 직접 연다.

### 검증 상태: ✅ 이미 됨

`tree-transplant/mcp_server/src/tree_transplant/canvas_server.py` 가 정확히 이 구조다.

| 요구사항        | 구현                                                                                                        |
| --------------- | ----------------------------------------------------------------------------------------------------------- |
| 로컬 HTTP 서버  | `ThreadingHTTPServer(("127.0.0.1", 0), handler)` — 포트 `0`이라 **빈 포트 자동 할당**(충돌 없음) |
| 백그라운드 실행 | `threading.Thread(..., daemon=True)` — MCP 응답을 막지 않음                                              |
| 브라우저 오픈   | `webbrowser.open(url)`, 실패해도 예외 삼키고 URL 반환                                                     |
| 링크 제공       | `open_canvas()`가 `http://127.0.0.1:<port>/?session_id=...` 반환                                        |
| 중복 기동 방지  | 모듈 전역 +`threading.Lock`으로 서버 1개만                                                                |

### ⚠️ 반드시 지켜야 할 함정 3개

1. **stdout을 절대 오염시키지 말 것.** stdio 트랜스포트는 stdout이 곧 JSON-RPC 채널이다. HTTP 서버가 접근 로그를 stdout에 찍는 순간 MCP 연결이 깨진다.
   → 우리 코드는 `log_message()`를 빈 함수로 오버라이드해 막아뒀다. Node로 짠다면 `console.log` 전면 금지, 로그는 `console.error`(stderr)로.
2. **MCP 엔드포인트와 캔버스 라우트를 분리할 것.** 브라우저로 `/mcp`를 열면 안 된다(브라우저는 MCP 메시지를 안 보냄). 캔버스는 완전히 별개의 일반 HTTP 라우트.
3. **`127.0.0.1`에만 바인딩할 것.** `0.0.0.0`으로 열면 같은 Wi-Fi의 타인이 세션 파일(코드·경로·API 키 포함)을 다 본다. 이건 보안 사고다.

### 알려진 제약

- 플러그인이 업데이트되면 `${CLAUDE_PLUGIN_ROOT}` 경로가 바뀐다. 실행 중인 MCP 서버는 **이전 경로를 계속 쓴다** → `/reload-plugins` 필요. (상태를 `${CLAUDE_PLUGIN_ROOT}`에 쓰지 말 것)
- 데스크톱 앱은 로컬 디렉토리 플러그인 등록을 아직 지원 안 함 → **개발/시연은 CLI에서**.

## 2. Node.js 기반 — 가능하지만 대가가 있다

### 되는 건 확실함

공식 플러그인 레퍼런스에 Node 예시가 그대로 있다:

```json
{
  "mcpServers": {
    "routines": {
      "command": "node",
      "args": ["${CLAUDE_PLUGIN_ROOT}/server.js"],
      "env": { "NODE_PATH": "${CLAUDE_PLUGIN_DATA}/node_modules" }
    }
  }
}
```

### 그런데 `node_modules`가 문제다

플러그인은 **git 저장소 클론으로 배포**된다. `node_modules`는 안 따라온다. 공식 해법은 `SessionStart` 훅으로 최초 1회 설치:

```json
{
  "hooks": {
    "SessionStart": [{ "hooks": [{
      "type": "command",
      "command": "diff -q \"${CLAUDE_PLUGIN_ROOT}/package.json\" \"${CLAUDE_PLUGIN_DATA}/package.json\" >/dev/null 2>&1 || (cd \"${CLAUDE_PLUGIN_DATA}\" && cp \"${CLAUDE_PLUGIN_ROOT}/package.json\" . && npm install) || rm -f \"${CLAUDE_PLUGIN_DATA}/package.json\""
    }]}]
  }
}
```

- `${CLAUDE_PLUGIN_DATA}` = `~/.claude/plugins/data/{plugin-id}/` — **플러그인 업데이트를 넘어 살아남는** 영속 디렉토리.
- `diff`로 `package.json` 변경을 감지 → 최초 설치와 의존성 변경 업데이트를 둘 다 커버.
- 실패 시 복사본을 지워 다음 세션에 재시도.
- 단, 이 훅은 **셸 문법(`diff`, `||`)**이라 Windows 순정 환경에서 그대로 도는지 별도 검증 필요. ← **실측 항목**

Python(uv)도 `uv sync`가 필요하니 사전 준비가 있는 건 마찬가지다. 차이는 **의존성 개수**다.

### Node.js가 깔려 있다는 보장이 없다 ← 놓치기 쉬운 포인트

Claude Code는 이제 **네이티브 인스톨러가 기본**이고 npm 설치 경로는 지원 중단 수순이다. 즉 "Claude Code 사용자 = Node 보유자"라는 가정이 **더 이상 성립하지 않는다.**
→ Node를 고른다고 런타임 요구사항이 사라지지 않는다. Python이든 Node든 사전 설치는 어차피 필요하다.

## 3. 의존성 비교

### A. 현행 Python 경로 (권장)

| 항목               | 내용                                                                  |
| ------------------ | --------------------------------------------------------------------- |
| 런타임             | Python ≥3.10,[uv](https://docs.astral.sh/uv/)                         |
| 패키지 의존성      | **`mcp>=1.0.0` 단 하나** (FastMCP 포함)                       |
| HTTP 서버          | 표준 라이브러리`http.server` — 무의존                              |
| 브라우저 오픈      | 표준 라이브러리`webbrowser` — 무의존                               |
| `claude -p` 호출 | 표준 라이브러리`subprocess` — 무의존                               |
| 프론트엔드         | `static/canvas.html` — **빌드 스텝 없는 순수 SVG**, 의존성 0 |
| 설치               | `uv sync`                                                           |

**총 서드파티 패키지: 1개.** 심사에서 "가볍다"고 말할 수 있는 수준.

### B. Node.js로 재작성할 경우

| 항목             | 패키지                                            | 비고                                      |
| ---------------- | ------------------------------------------------- | ----------------------------------------- |
| MCP SDK          | `@modelcontextprotocol/sdk`                     | **버전 전환기 리스크** — 아래 참조 |
| 스키마 검증      | `zod`                                           | SDK가 사실상 요구                         |
| HTTP 서버        | Node 내장`http`                                 | 무의존 가능 (express 불필요)              |
| 브라우저 오픈    | `open` 또는 내장 `child_process`              | 내장으로 대체 가능                        |
| 프론트엔드(선택) | `tldraw` / `reactflow` + `react` + `vite` | **여기서 폭발**                     |

**⚠️ SDK 버전 타이밍이 최악이다.**
`@modelcontextprotocol/sdk`는 v1.29.0이 현재 안정판인데, **v2가 2026-07-28 MCP 스펙 대상으로 베타 중**이고 패키지가 `@modelcontextprotocol/server` / `@modelcontextprotocol/client`로 **분리**된다. 정식 릴리스 예정일이 **7월 28일 — 우리 공유일(7.24) 바로 다음 주**다.
지금 Node로 시작하면 대회 기간 중 SDK 메이저 전환을 정면으로 맞는다. (v1은 v2 출시 후 최소 6개월 유지되므로 v1 고정은 가능하지만, "최신 아님" 부담)

**⚠️ tldraw/React Flow는 빌드 스텝을 강제한다.**
현재 `canvas.html`은 빌드 없이 브라우저가 바로 연다. React 기반 라이브러리를 쓰면 `npm run build` → 번들 산출물을 저장소에 커밋하거나 설치 시 빌드해야 한다. 플러그인 배포 난이도가 한 단계 올라간다.

### 왜 Node.js를 염두에 두는가

위 표는 Node의 "비용"만 나열하지만, 그럼에도 Node로 기우는 데는 타당한 이유가 있다. 아직 최종 확정은 아니고 방향을 잡는 수준이다.

1. **시각화가 제품의 핵심 가치다.** 성숙한 캔버스 라이브러리(React Flow, tldraw) 생태계가 사실상 JS/TS에 집중돼 있다. 우리가 원하는 트리 렌더 품질을 가장 빠르게 뽑을 수 있는 곳이 여기다.
2. **프론트가 어차피 JS라, 서버까지 Node면 언어가 하나로 통일된다.** 팀이 프론트/백을 같은 문법으로 오가며 개발하고, 트리 노드 스키마·검증 로직 같은 것을 **양쪽이 공유**할 수 있다. 컨텍스트 스위칭 비용이 준다.
3. **참고 자산이 많다.** MCP의 TS SDK·예제·커뮤니티 문서가 풍부해, 막힐 때 근거를 찾기 쉽다.
4. **미래 확장성.** 이후 B안(VS Code/Cursor 확장)으로 넓힐 때 확장 호스트가 Node 런타임이라 코드 재사용이 자연스럽다.

**단, 단정하기엔 이르다 — 반대 근거도 여전히 유효하다.** Python안은 서드파티 의존성 1개로 가볍고 재사용 자산(`session_tree.py`)이 있으며, 네이티브 인스톨러로 Claude Code를 깐 사용자는 Node가 없을 수 있다(§2). 따라서 최종 결정 전에 §5 실측 항목(특히 **Node 18+ 존재 여부**, **esm.sh 접근 가능 여부**)으로 검증한 뒤 굳히는 게 맞다.

## 4. 현재 방향: Node.js

**시각화 품질을 우선해 현재는 Node.js 쪽으로 기울어 있다.** 시범 재작성으로
§3에서 지적한 Node의 비용을 아래 방식으로 대부분 제거할 수 있음을 확인했다.

| §3에서 지적한 Node의 비용                                | 실제 대응                                                                                                                                             |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@modelcontextprotocol/sdk` v2 전환기 리스크            | **SDK를 쓰지 않음.** 필요한 프로토콜 표면이 `initialize`/`tools/list`/`tools/call` 셋뿐이라 `server/mcpStdio.js`에 직접 구현 (약 140줄) |
| `node_modules` 배포 + SessionStart 훅 + Windows 셸 문법 | **의존성 0개 → 훅 자체가 불필요.** 클론 그대로 실행                                                                                            |
| tldraw/React Flow의 빌드 스텝                             | **importmap + esm.sh CDN.** `npm run build` 없음, HTML 파일 하나                                                                              |

결과적으로 서드파티 패키지 수는 Python안(1개)보다도 적은 **0개**가 됐다.
대신 새로 생긴 비용이 하나 있다: **캔버스 최초 렌더에 인터넷 연결이 필요**하다
(esm.sh에서 React/React Flow를 받아옴). CDN 실패 시 안내 문구를 띄우도록 폴백을 넣었고,
캔버스 없이 트리를 보려면 `get_tree_json` 도구가 대안이 된다.

**참고: 캔버스 언어와 서버 언어는 원래 무관하다.**
이번 구현에서도 캔버스는 브라우저 React Flow, 서버는 별개다.
Node를 고른 실익은 "언어를 하나로 통일해 팀이 프론트/백을 같은 문법으로 만진다"는 쪽이지,
"React Flow를 쓰려면 Node여야 한다"가 아니었다.

# compact 기법 종류 (공통 조사) — 가지 압축 기능 설계 근거

## A. 개념 먼저

- **context window** = 모델이 한 번에 보는 토큰 전부(시스템 프롬프트 + 대화 + 툴 결과 + 주입 파일). 유한하고, **다 차기 전에도** 채울수록 품질이 떨어짐("context rot"). → 관리 대상은 "크기"가 아니라 **밀도·충실도**.
- **`/compact`** = 대화를 요약본으로 대체(+도구에 따라 최근 파일·todo 복원). `/clear`(전체 삭제)와 다르고, truncation(맹목적 잘라내기)보다 의미 보존이 나음. **손실적**이며 다회 반복 시 누적 열화.
- 업계 합의 트리거 임계치: **70~85%** (95%는 늦음).

## B. 기법 종류 (단순 → 정교)

| #  | 기법                                 | LLM 호출       | 프롬프트에 넣는 양                | 손실          | 연속성 |
| -- | ------------------------------------ | -------------- | --------------------------------- | ------------- | ------ |
| ① | Truncation / Sliding window          | **없음** | — (오래된 것 폐기)               | 높음(맹목)    | 낮음   |
| ② | 토큰 트리밍(max_token_limit)         | **없음** | —                                | 중            | 낮음   |
| ③ | 롤링 요약(rolling summary)           | 1회            | **전체**                    | 중            | 중     |
| ④ | **요약+버퍼 하이브리드(표준)** | 임계 시        | **밀려나는 오래된 부분만**  | 중(최근 보존) | 높음   |
| ⑤ | 계층/맵리듀스 요약                   | 여러 회        | 전체를 청크로 분할                | 중            | 중     |
| ⑥ | **앵커드 증분(delta)**         | 증분마다       | **직전 요약 + 새 메시지만** | 낮음          | 최상   |
| ⑦ | 가지치기(pruning)                    | 없음/적음      | — (툴 출력만 제거)               | 낮음          | 높음   |
| ⑧ | RAG / 장기 메모리                    | 검색 시        | 필요분만 검색 주입                | 낮음(선택)    | 높음   |
| ⑨ | 서브에이전트 격리                    | 격리           | 별도 컨텍스트, 요약만 회수        | 낮음          | 높음   |

**핵심 통찰: "compact = 전체를 다시 LLM에 넣기"는 ③(가장 단순·비쌈)에만 해당.**

- ①②⑦은 애초에 LLM을 안 씀(삭제·트리밍).
- ④는 전체가 아니라 밀려나는 부분만, ⑥은 직전 요약+델타만 넣음 → 전체 재요약 회피.
- ⑤는 전체를 넣되 청크로 쪼개 여러 번(병렬).
- 예외: Codex는 서버측 처리 + session memory로 **LLM 호출을 건너뛰기도** 함.

## C. 계층 / 맵리듀스 / 앵커드 상세

**맵리듀스(Map-Reduce)** — 긴 내용을 청크로 나눠 **각 청크를 병렬 요약(map)** → 부분 요약들을 **합쳐 최종 요약(reduce)**. 합칠 게 또 크면 재귀적으로 축소(collapse). 장점: 병렬이라 빠름. 약점: 청크끼리 서로를 몰라 **경계를 가로지르는 인과·흐름이 흐려짐**.

**계층(Hierarchical)** — 맵리듀스를 **트리로 일반화**. 원문 → 문단 → 섹션 → 전체로 의미 단위를 따라 접어 올림. **중간 층 요약을 보존**해 특정 가지만 펼쳐볼 수 있는 게 강점.

**앵커드 증분(Anchored iterative / delta)** — 매번 전체를 다시 요약(full-reconstruction)하지 않고, **지속되는 요약 상태(anchor)에 새 내용만 병합**. `새 요약 = f(이전 요약, 새 메시지)`. Factory 실측(실제 세션 3.6만 건)에서 full-reconstruction보다 **정확도·완전성·연속성이 일관되게 높음**(판단 기준이 안 흔들려 확정된 정보가 유실 안 됨). 약점: 초기 오류가 닻에 박히면 전파됨.

→ **순차성 스펙트럼**: 맵리듀스(병렬·맥락약함) ↔ 계층(트리·부분보존) ↔ 앵커드/refine(순차·맥락강함).

## D. tree-transplant "가지 압축(extract)"에 대한 결론

- 한 가지는 **시간순 단일 흐름** → 맵리듀스보다 **앵커드 증분/계층**이 품질상 적합(연속성).
- **⚠️ 비용 트레이드오프(반영):** 우리는 가지를 `claude -p`(구독 요금 내)로 압축한다. **롤링 방식(③)으로 매번 가지 전체를 넣으면 긴 가지에서 호출 토큰·지연이 선형으로 커진다.** → **앵커드 증분(⑥)** 채택 시, 노드가 늘 때마다 델타만 처리해 **호출 비용·지연을 크게 절감**. 각 노드(또는 구간)에 갱신된 요약 상태를 함께 저장해두면, 사용자가 임의 지점의 "여기까지 요약"을 즉시 꺼내 이식 가능.
- 닻 전파 오류 방지를 위해 **요약 상태를 사용자가 직접 보고 수정·고정**하는 편집 지점 제공.
- 계층 방식의 "중간 요약 보존"은 **트리 UI와 직결**: 노드 접으면 서브트리 섹션 요약, 펼치면 원문.
- 이식이 메인이므로 요약은 **투명한(사람이 읽는) 텍스트**여야 함 — Codex식 암호화 blob 부적합.
