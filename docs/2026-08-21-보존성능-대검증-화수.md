# 압축 보존 성능 대검증 — 리트리버·임베딩·공유메모리 (2026-08-21, 화수)

후속 에이전트가 압축본으로 작업을 이어갈 때 **손실이 실제로 얼마나 방어되는지**를,
층별로 분리해 측정한 라운드의 결과 정본입니다. 과장 없이, 자기 교정 과정까지 기록합니다.
관련 PR: #21·#22(리트리버), #31(공유메모리·압축 갈래 검색). 총 측정 비용 ~$38.

## 1. 결론 요약

| 질문 | 답 | 근거 절 |
|---|---|---|
| 압축 손실이 방어되는가 | **범위 안 사실 84~91%, 역사 의존 사실 9%→59%** | §4·§5 |
| 각 층이 값을 하는가 | 동봉 +5/34, 용어부록 +5/34, 대화형 소비 +11~12/34, 임베딩 주입 +1/34 | §5 |

**핵심 발견**: 보존율을 좌우하는 지배 변수는 개별 기능이 아니라 **압축본의 소비 방식**이다.
같은 패키지를 엄격 일괄 QA로 물으면 24%, 대화형으로 하나씩 물으면 56~59%를 꺼낸다.

## 3. 손실의 두 종류 — 측정 전에 갈라야 하는 구분

- **범위 안 사실**: "그 구간에서 무엇을 했나". 압축이 원문의 ~41%를 버리며 생기는 손실.
- **역사 의존 사실**: "그 작업의 과거 맥락(이전 세션의 결정·수치)". 요약이 애초에 담지 않는 손실.

기존 팀 측정(61세션 87%)은 전자를, 이번 역사 평가는 후자를 잰다. 두 숫자는 다른 것을 잰다.

## 4. 측정 ① — 과거가 없는 데이터에서의 동봉 (3조건 · 20세션 · 200문항)

팀 키트의 질문지·채점을 그대로 쓰고 압축본만 3종으로: 동봉 OFF / 키워드만 / 하이브리드.

- 결과: **±0** (ON 77.0% vs OFF 78.5%, CI [-4.0,+1.0], p≈0.51) · 임베딩 동봉 기여 80건 중 1건
- 원인 확인: 이 데이터는 압축 범위가 전부 세션 처음부터라 **범위 이전 턴이 0개** —
  되찾을 과거 자체가 없음. 동봉의 존재 이유(과거 회수)가 성립 안 하는 구조.
- 함께 확인: 같은 데이터에서 팀의 소비 시점 검색 A/B는 +6.6%p(84.4→91.0) —
  "미리 붙이기"보다 "필요할 때 찾기"가 유효하다는 첫 신호.

## 5. 측정 ② — 과거가 실재하는 데이터 (4조건 · 5프로젝트 · 34문항 · $12)

**질문 설계**: "마지막 세션의 작업을 묻되, 완전한 답에 이전 세션의 사실이 필요"한 문항을
LLM 생성(근거 턴 라벨 포함). 무맥락 대조군 **0/34** — 질문 누수 없음 확인.

| 조건 | 정답 | 비고 |
|---|---|---|
| A: 요약만 (엄격 일괄 채점) | 3/34 (9%) | 역사 의존 질문엔 요약만으론 거의 전멸 |
| C: A + 정적 동봉 | 8/34 (24%) | **회수 5 · 퇴행 0** |
| G: C − 용어부록 | 3/34 | **용어부록 층 제거 시 5건 소실** |
| D: 갈래 대화형 (발췌 주입) | **20/34 (59%)** | 회수 18 · 퇴행 1 · 주입 34/34 |

### 자기 교정 — D의 우위는 검색이 아니라 소비 방식이었다

D의 압승을 검증하기 위해 **주입을 끄고(D-noEmbed) 20건을 재실행**한 결과 **19건이 그대로 정답**.
즉 D의 이득 분해:

```
+11~12건  대화형 소비 방식 (1문항씩, 유연한 프롬프트)   ← 지배 변수
 +5건     정적 동봉
 +5건     용어부록 층
 +1건     발췌 주입 (임베딩)
```

교훈 둘: ① 압축본은 엄격 일괄 QA가 시사하는 것보다 훨씬 많은 정보를 보존한다 —
평가 프로토콜이 보존율을 과소평가할 수 있다. ② 극적인 결과는 절제 실험으로 분해해야 한다
(안 했으면 "검색이 0→59%를 만들었다"는 과장을 보고할 뻔했다).

## 6. 임베딩 판정 — 4개 환경 종합

| 환경 | 기여 |
|---|---|
| 한국어 검색창 (패러프레이즈) | r@3 11.1→**22.2%** (2배) |
| 교차언어 (한 질문↔영 로그) | **주입 성사 100% 임베딩 의존**(키워드 0건), 답 기여 +1 |
| 영어 동봉·검색 | ~0 (80건 중 1건, 이득 없음) |
| 실프로젝트 압축 | 가끔 (4건 중 1건) |

**판정: "선택 설치 + 무손실 폴백" 현행 유지.** 필수 승격 근거 없음(1.2GB 대비),
제거 근거도 없음(한국어 사용자·교차언어 검색에 실기여). 한국어로 영어 작업 기록을
검색하는 사용자에게는 설치 권장.

## 7. 공유메모리(용어부록 캐시) 판정 — 양면 실측 통과

- **보존 기여**: +5/34 (§5의 G↔C) — 층을 빼면 제3자 데이터에서 정답 5건이 사라짐
- **비용**: 동일 범위 2회 압축 리플레이(실프로젝트)에서 용어부록 $0.697→**$0.203(-70.9%)**,
  히트 16/24, 공통 16개 정의문 **글자까지 동일**(품질 무손상), 미스 0이면 LLM 호출 생략
- **안전**: 로그 append-only라 최초 정의 턴 불변 → 무효화 불필요가 구조적으로 성립
- 한계: 누적 히트율 곡선은 실사용 로그(`캐시 히트 N/미스 M`)로 추적 예정.
  42.7%는 과거 압축 6건의 역사적 재사용률(재측정 아님)

## 8. 검증 강도 등급 (정직 고지)

- **견고**: 소비 방식 지배(절제 실험 통과) · 동봉/용어부록 기여(짝비교+대조군) ·
  과거 없는 데이터 ±0(팀 질문지) · 공유메모리 비용/품질(리플레이+산출물 대조)
- **방향성**: 임베딩 +1/20(n 소) · 라이브 검색 실사용 가치(자체 실증)
- **미검증**: 절대 보존율의 통계적 확정 · 사람 출제 기준 성능 · 한국어 프로젝트 데이터 ·
  MaxDevv 10프로젝트(구축만 완료)

질문 생성·채점이 LLM(sonnet)이라는 한계는 전 측정 공통. 공식 수치는
**팀원 로그 수집(15~20 프로젝트/3~4명, 사람 출제 질문지)**이 유일 경로 — 설계안은
